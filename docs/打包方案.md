> 日期：2026-10-13 ｜ 状态：**待你选路线**
> 结论：**两条都做约 9–13 个工作日；只做一个约 4–6 个工作日。**
> 但真正卡脖子的不是打包，是**语音**（见第 4 节）。
>

## 1. 现状：这个项目几乎是"为打包而生"的

刚审计了一遍，条件比一般 H5 项目好很多：

| 检查项 | 实测结果 | 对打包的意义 |
|---|---|---|
| 构建产物 | **1.54 MB / 6 个文件** | 装进任何壳都是小体积 |
| 网络请求 | **零**（全静态资源） | 天然离线，不需要服务器 |
| 资源路径 | 全部相对路径（`base: './'`） | `file://` 与自定义协议都能用 |
| 后端 | 没有 | 不需要域名、备案、服务器 |
| 存储 | IndexedDB，且在 `ProgressStore` 接口后面 | 换平台存储只改一个实现 |
| 音频 | `AudioBus` 接口后面 | 同上 |
| 平台出口 | `PlatformServices`（当初就是为这个留的） | 新平台 = 写一个新实现，**游戏代码一行不改** |

**关键：浏览器 API 的接触面只有 4 处** —— `platform/web.ts`（IndexedDB / AudioContext / 语音）、
`stores/locale.ts`（localStorage）、`createGameContext.ts`（matchMedia）、Phaser 自己的 RAF。
其余全部代码都对平台无感。

## 2. 三条路线

| 路线 | Windows | Android | 安装包体积 | 上手难度 | 说明 |
|---|---|---|---|---|---|
| **A. PWA** | Edge/Chrome「安装应用」 | Chrome「添加到主屏幕」 | 不产生安装包 | ★ | **0.5–1 天**，立刻能在两端"像 App 一样"玩，但分发不如安装包直接 |
| **B. Tauri 2（统一）** | Tauri | Tauri（移动端） | ~8 MB（估算） | ★★★★ | 一套配置两个平台，最优雅；但 Android 端较新，要装 Rust + Android NDK |
| **C. Tauri/Electron + Capacitor（稳妥）** | Tauri 或 Electron | Capacitor | Tauri ~8 MB（估算）/ Electron ~150 MB | ★★★ | 每个平台都用最成熟的方案；代价是两套工具链 |

**我的建议：路线 C，其中 Windows 用 Tauri。**

- **Android 必须用 Capacitor** —— 它是"Web 应用套安卓壳"的行业标准，成熟度无可替代。
  Capacitor 会在 WebView 里跑一个本地服务（`http://localhost`），所以 ES module、IndexedDB、WebGL 全部正常。
- **Windows 推荐 Tauri 2** —— 用系统自带的 WebView2，产物只有几 MB（估算值，实测以产物为准）；
  而且它默认走自定义协议，**规避了 Electron 的一个经典坑**（见下）。
- **不推荐 Electron 的原因**：产物 150 MB 起；而且我们的 `index.html` 里有
  `<script type="module" crossorigin>`，用 `file://` 加载时 Chromium 会因 CORS 拒绝执行 module script，
  必须额外注册自定义协议或改成非 module 产物 —— 多一个坑，换来一个 150 MB 的包。

## 3. 工作量拆解（按 1 人 / 熟悉前端但不一定写过移动端估）

| 阶段 | 内容 | 估时 |
|---|---|---|
| **A. 打通骨架** | Capacitor 接入 + 安卓竖屏锁定 / 全屏 / 安全区；Tauri 接入 + 窗口按手机比例；两端跑通"启动 → 玩一局 → 退出" | **2–3 天** |
| **B. 平台适配层** | 写 `desktop` 与 `native` 两个 `PlatformServices` 实现：音频、存储、生命周期、分享、返回键 | **2–3 天** |
| **C. 两端界面适配** | 桌面：竖屏窗口 + 鼠标 hover 反馈；安卓：刘海/手势条安全区、沉浸全屏、返回键"先回游戏馆再退出" | **1.5–2 天** |
| **D. 打包与分发打磨** | 图标多尺寸、启动图、应用名（中英）、版本号；Windows 的 NSIS 安装包 + 便携版；安卓签名 keystore + release 构建 | **1.5–2 天** |
| **E. 真机验证与修 bug** | 安卓模拟器 + 1–2 台真机（重点测低端机 WebGL 帧率）；Windows 不同 DPI/缩放 | **2–3 天** |
| | **合计** | **9–13 个工作日** |

**只做一个平台：约 4–6 个工作日**（安卓和 Windows 的工作量差不多）。

如果先做路线 A（PWA）打底，**0.5–1 天**就能让人在电脑和安卓手机上玩到，之后再决定要不要装壳。

## 4. 真正的风险：语音（这条必须提前知道）

我们的旁白现在**全部靠浏览器 TTS**（`speechSynthesis`）。问题是：

| 平台 | `speechSynthesis` 支持情况 |
|---|---|
| Windows + WebView2（Tauri） | ✅ 支持，走系统语音 |
| Windows + Electron | ⚠️ 时好时坏，不同版本表现不一致 |
| **Android WebView（Capacitor）** | ❌ **不支持**。Chrome 浏览器支持，但 WebView 没有实现 Web Speech API |

也就是说：**现在的做法套上安卓壳之后，旁白会全部没有声音。**

三条出路，建议**同时做前两条**：

1. **接原生 TTS 插件**（`@capacitor-community/text-to-speech` → 安卓系统 TTS 引擎）。
   工作量约 **0.5–1 天**。因为 `AudioBus` 接口当初就是为这个留的，改的是一个实现文件，游戏代码不动。
2. **加降级兜底**：检测不到 TTS 就不朗读，只保留音效，**不能让游戏报错或卡住**。
   工作量约 **0.5 天**。
3. （可选，质量最好）**预生成音频文件**：用 TTS 批量生成 mp3 打包进去，两端都能播，音质稳定可控。
   代价是体积（两个典故约 1–2 MB）和一条生成流水线，工作量 **1–2 天**。
   这条路迟早要走（真人配音也要走），但不必卡在打包这一步。

> 这一条是本次评估里**最可能超出预期**的地方，因为它依赖"真机实测"，不是写代码就能确定的。

## 5. 分发与合规（不写代码，但要提前决定）

| 事项 | 说明 | 成本 |
|---|---|---|
| Windows 代码签名 | 不签名的话，别人下载 exe 会被 SmartScreen 拦（"未知发布者"） | 证书约 ¥1000–3000/年 |
| 安卓签名 | 必须；自己生成 keystore 即可，免费 | 免费，但要**保管好**，丢了无法覆盖更新 |
| 直接发 APK 文件 | 最省事。用户在设置里允许"安装未知来源"即可 | 免费 |
| 上 Google Play | 需要 AAB、目标 SDK 要求、隐私政策，且**儿童类应用受 Families 政策约束**（更严） | 注册费 $25 + 合规成本 |
| 上国内安卓商店 | 需要软件著作权登记、企业主体、备案 | 数周 + 费用 |

**建议**：先做"直接分发"（exe + apk 文件），跑通体验再考虑上架。

## 6. 建议的推进顺序

1. **路线 A：PWA（0.5–1 天）** —— 立刻让两端都能玩，先验证"大家在电脑和手机上玩"这件事本身
2. **安卓壳（4–6 天）** —— 手机是主场景，优先做
3. **Windows 壳（4–6 天）** —— 可复用第 2 步的适配层实现
4. **预生成音频（1–2 天，可选）** —— 想要稳定音质时再做
