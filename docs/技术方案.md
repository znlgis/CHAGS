# CHAGS 中国历史典故儿童游戏合集 · 技术方案 v1.1

> 状态：**持续更新** ｜ English: [docs/en/architecture.md](en/architecture.md)
> 本文档只定技术路线与架构，具体典故的玩法设计见《典故方案-*》。
> 日期：2026-10-13 ｜ 变更：外壳框架 React 19 → **Vue 3.5**；TypeScript 基线 7.0.2 → **5.9.3**（实测约束，见 2.3）
> 一句话结论：**用 Phaser 4 + Vue 3.5 的“H5 优先”方案，按“外壳 + 引擎 + 玩法模板 + 内容数据 + 独立游戏包”五层架构来做，每个典故是一个可独立开发、独立打包、懒加载的游戏模块，玩法骨架靠模板复用，典故内容靠 JSON 驱动。**

## 0. 结论速览（TL;DR）

| 决策项 | 选型 | 一句话理由 |
|---|---|---|
| 游戏引擎 | **Phaser 4.2**（TypeScript 一等公民，MIT） | 纯代码、可 diff、可单测，最适合“一个小游戏一个小模块”的合集形态 |
| 应用外壳 | **Vue 3.5（SFC + Composition API）+ Pinia + Tailwind 4** | 大厅/图鉴/历史长卷/家长中心是 UI 密集型，SFC 单文件组件写起来最快 |
| 语言 | **TypeScript 5.9.3**（strict） | 引擎与游戏之间靠接口契约隔离；**不是 7.0.2，原因见 2.3（已实测）** |
| 构建 | **Vite 8 + pnpm workspace** | 原生多入口 + 代码分割，每个游戏自动独立 chunk |
| 内容 | **JSON + zod schema，构建期校验** | 换典故 = 换内容，不用改代码 |
| 玩法 | **玩法模板库（12 个模板）** | 让“第 30 个典故”的成本远低于“第 1 个” |
| 存储 | **IndexedDB（本地优先）+ 可替换接口** | 无后端、无广告、无个人信息采集，儿童合规最安全 |
| 离线 | **PWA（Service Worker 预缓存）** | 弱网/断网可玩，可“添加到主屏幕” |
| 测试 | **Vitest（逻辑）+ vue-tsc（SFC 类型）+ Playwright（冒烟/截图）+ 内容校验脚本** | 一条 `pnpm verify` 命令全绿才算完成 |
| 后端 | **MVP 阶段完全不做** | 纯静态站点，部署最便宜、最稳、最合规 |

**三条架构铁律**（后面所有设计都服从它们）：

1. **逻辑与渲染分离** —— 计分、判定、调度等规则写在纯 TS 模块里，不 import Phaser，可以脱离浏览器单测。
2. **游戏不得自己碰环境** —— 存档、音频、生命周期、分享一律通过注入的 `GameContext`，禁止游戏内部直接 `localStorage` / `fetch` / `wx.*`。这是将来上微信小游戏/云存档的唯一低成本出口。
3. **每个游戏必须能被“无头直达”** —— 支持 `#/play/<id>?seed=fixed&autoplay=1`，否则自动化测试和 AI 协作都做不了。

## 1. 从产品定位反推技术约束

定位：**给小朋友（6–12 岁）玩的中国历史典故合集，重点不是“玩过”，而是“记住 + 理解寓意”**。

这个定位直接决定了 8 条硬约束，全部会写进架构：

| # | 产品诉求 | 技术约束 |
|---|---|---|
| 1 | 家长随手就把手机给孩子，不能要求装 App | H5 / PWA，扫码即玩；不做原生 |
| 2 | 小朋友注意力短，单局 3–5 分钟 | 无长连接、无加载等待、随时中断可恢复 |
| 3 | 场景常在车内/老家/弱网 | 静态资源 + Service Worker 预缓存，离线可玩 |
| 4 | 家里的旧安卓机、旧 iPad 也要能跑 | 2D、体积预算、低端机降级策略 |
| 5 | **核心指标是“记住”** | 内容数据结构必须内建“关键抉择点 / 常见误解 / 迁移练习 / 复习间隔” |
| 6 | 合集要能长到 30–100 个典故 | 模块化 + 契约化 + 模板库，新增典故 = 加一个包 + 一份 JSON |
| 7 | 儿童产品，家长会问隐私 | 无广告 SDK、无社交、不采集儿童个人信息、数据默认只存本机 |
| 8 | 很可能由 AI 辅助/主导开发 | 全文本资产（可 diff）、可单测、一条命令验证、确定性随机 |

> 第 8 条不是小事：它直接否掉了 Cocos / Unity 这类“编辑器里拖拽出场景”的方案——那些工程的场景文件是二进制或巨型 JSON，无法 review、无法 diff、无法被自动化验证。

## 2. 技术选型（含对比与取舍）

### 2.1 引擎对比

| 方案 | 合集适配度 | 微信小游戏 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|---|
| **Phaser 4.2** | ★★★★★ | 需适配（见 3.8） | 纯代码/TS、MIT、生态成熟、ESM 可摇树、包可控 | 无编辑器，UI 要自己写 | ✅ **主选** |
| Phaser 3.90 | ★★★★☆ | 社区有适配经验 | 教程/示例最多 | 已是上一代，新项目无理由 | 备选（仅当小游戏 PoC 失败） |
| Cocos Creator 3.x | ★★★☆ | ★★★★★ 一键发布 | 中文生态好、编辑器完善、小游戏首选 | 场景/预制体是编辑器资产，AI 与 CI 不友好；包体大；学习曲线陡 | 备选（仅当“微信小游戏”是硬性首发要求） |
| PixiJS | ★★☆ | 无 | 渲染性能好、体积小 | 只是渲染器，游戏框架要从零造 | ✗ |
| Godot 4 Web | ★★☆ | 不支持 | 开发体验好 | Web 导出体积 30MB+，移动端浏览器兼容差 | ✗ |
| Unity WebGL | ★ | 不支持 | 3D 强 | 移动端 H5 基本不可用 | ✗ |
| 纯 DOM/CSS | ★★★（仅问答类） | 可 | 最轻、可 SEO、可无障碍 | 复杂交互（拖拽/物理/棋盘）做不动 | 仅用于图鉴、复习测验等非核心玩法 |

**为什么选 Phaser 4 而不是 Phaser 3：** Phaser 4.0.0 于 2026-04 正式发布，4.2.1 于 2026-07 发布，已迭代半年且是 npm `latest`。新项目在 2026-10 没有理由从上一代起步；代价是部分网络教程仍是 Phaser 3 写法（官方有迁移指南）。

**实测引擎体积**（`phaser@4.2.1/dist/phaser.min.js`，完整版）：

- 未压缩 **1,375,976 字节**
- gzip 后 **357,778 字节（≈350 KB）**

这个数字决定了“引擎绝不打进主包”——只有进入游戏时才加载，且加载一次后浏览器长期缓存。

### 2.2 外壳：Vue 3.5 还是全 Phaser？

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Vue 3.5 外壳 + Phaser 游戏（选）** | 大厅/图鉴/长卷/设置/家长中心用 DOM 写得又快又好；SFC 单文件组件把模板、逻辑、样式放在一起，改一个页面只动一个文件；Pinia 管进度状态；Phaser 被隔离进游戏包 | 两套心智 |
| 全 Phaser | 一套心智，包更小 | 在 Canvas 里做列表/滚动/表单/文字排版是自虐 |
| 原生 DOM 外壳（无框架） | 最轻 | 状态多起来后（进度/复习/图鉴/设置）会失控 |

关键：**Phaser 只出现在 `games/*` 与 `packages/phaser-kit` 里，外壳主包 import 不到它**，所以外壳首屏永远不会付那 350 KB。

**Vue 版本说明**：Vue 3.6 目前仍是 RC（`3.6.0-rc.11`，含 Vapor 模式），**生产用 3.5.44 稳定版**。`@vitejs/plugin-vue@6` 的 peer 已经是 `^3.2.25 || ^3.6.0-rc.10`，所以 3.6 正式发布后升级只是改一行版本号。

**Vue × Phaser 集成踩坑清单（这段是血泪，写进 code review）**：

1. **Phaser 实例必须用 `shallowRef` 或 `markRaw` 持有**。用 `ref` 会让 Vue 的响应式系统深度遍历整个 Phaser 对象图（场景、纹理、WebGL 上下文），轻则卡顿，重则直接抛错。
2. **游戏容器不要放进 `<KeepAlive>` 或 `<Transition>`**。离开路由前必须 `await unmount()`，否则 Phaser 的 `requestAnimationFrame` 循环和 canvas 会残留。
3. **给游戏模块加 HMR 边界**：编辑 Phaser 场景时应整页刷新（`import.meta.hot?.decline()`），否则热替换会叠出多个 canvas。
4. **不要在 `computed` / `watch` 里持有 Phaser 的 GameObject**，它们不是响应式数据。
5. 宿主组件最小实现就是 `defineProps` + `shallowRef` + `onMounted`/`onBeforeUnmount`（见 3.3 代码）。

> 🔴 **实测出来的硬约束：TypeScript 7 在本项目里用不了。**
> 本机验证：`typescript@7.0.2 + vue-tsc@3.3.13` → `ERR_PACKAGE_PATH_NOT_EXPORTED: './lib/tsc' is not defined by "exports"`。TS 7（Go 原生编译器）移除了 `./lib/tsc` 子路径导出，而 `vue-tsc` 依赖它，最新版 `vue-tsc@3.3.13` 同样失败；查 dist-tags 确认**不存在**支持 TS 7 的 vue-tsc 版本。
> 换到 `typescript@5.9.3` 后同一份代码立即正常工作，并正确报出 `src/Hello.vue(3,7): error TS2322`。
> 所以基线锁在 **TS 5.9.3**：它同时满足 `vue-tsc >=5.0.0`、`typescript-eslint <6.1.0`、`pinia >=5.6.0` 三方 peer 范围，是当前唯一“全绿”的版本。
> 代价：暂时享受不到原生编译器约一个量级的类型检查提速。等 `vue-tsc` 跟进后再评估升级（代码零改动）。

### 2.4 美术与资源管线

- 格式：**WebP**（兼容优先）/ AVIF（可选渐进增强）；序列帧一律打**纹理图集**（TexturePacker 或 free-tex-packer），单图 ≤ 200 KB。
- 分辨率：按 `@1x / @2x` 两档出图，`@3x` 不必要；逻辑分辨率 750×1334（竖屏）。
- 字体：**必须可商用**。推荐 思源黑体 / 霞鹜文楷 / 站酷快乐体（逐个核实授权），用 fontmin / subset-font 按用字**子集化**（中文全字库动辄 5–10 MB，子集化后可降到 100 KB 级）。
- 授权台账：建 `ASSETS-LICENSES.md`，每个字体/音效/音乐/BGM 记录来源与许可证。这是会踩死人的坑，从第一天就做。
- 风格：建议**圆润卡通 + 中国色（朱红/黛青/米黄/墨黑）**，所有典故共用一套角色与场景基件，降低后续 30 个典故的美术成本。
- **阶段 0 策略（已确认）**：美术全部用**几何图形绘制**（Phaser Graphics/Rectangle），零图片资源，先把玩法与学习闭环跑通；后续替换为贴图时**代码不用改**，只换资源与 `textures` 引用。

### 2.5 音频

- 引擎：Phaser 内建 WebAudio 能力，但**音频走 `PlatformServices.audio` 统一出口**（便于换平台与静音策略）。
- **iOS/微信必须用户手势解锁音频**——外壳在“开始游戏”的点击里统一做一次 unlock，之后游戏内才能自由播音。
- 旁白：按“幕”切成 3–8 秒小文件，**懒加载**；进入某幕才下载对应音频。
- 生成方式：先用 TTS 批量生成（快、便宜、可重录），关键成语/口诀再考虑真人录音。
- 双格式 `.m4a + .ogg`（iOS 认 m4a，安卓/桌面认 ogg），单文件 ≤ 100 KB。
- **阶段 0 策略（零资源）**：旁白用浏览器 `SpeechSynthesis`（zh-CN），音效用 WebAudio 振荡器合成。零音频文件即可验证“听”这一通道；接口不变，后期换成真音频只改 `AudioBus` 实现。

### 2.6 数据与存储

- **MVP 无后端**。进度、图鉴、复习计划全部存本机 IndexedDB（`idb-keyval` 或原生 API）。
- 统一从 `ProgressStore` 接口进出（见 3.3），将来接云存档只换实现。
- 存档结构**带 `schemaVersion` + `migrate()`**：现在写迁移函数几乎零成本，等有用户数据了再补就是灾难。

### 2.7 测试与质量保障

| 层级 | 工具 | 覆盖内容 |
|---|---|---|
| 类型 | `vue-tsc --noEmit` | 全仓 strict，含 `.vue` 单文件组件 |
| Lint | eslint 10（flat）+ eslint-plugin-vue + typescript-eslint | 风格 + 禁用危险 API（logic 目录禁用 `Math.random` / `Date.now`） |
| 逻辑单测 | Vitest | `logic/` 与 `packages/progress` 纯函数：判定、计分、复习调度、种子随机数 |
| 内容校验 | 自研脚本 `content:check` | zod schema + 模板关卡校验 + 引用资源存在性 + 必填字段完整性 |
| 端到端 | Playwright | 每款游戏 URL 直达 → 自动通关 → 断言完成事件 + 截图基线 |
| 体积 | size-limit | 主包 / 单游戏 chunk 预算守卫（阶段 1 接入） |

**一条命令： `pnpm verify` = typecheck → lint → test → content:check → build。**

对 AI 协作来说，这条命令就是“完成”的定义——它必须全绿。

### 2.8 部署

- 纯静态产物，CDN 分发。海外/通用：Cloudflare Pages；**面向国内**：阿里云 OSS + CDN 或腾讯云，需**已备案域名**（要上微信生态，备案是硬门槛，建议尽早办）。
- PWA：`vite-plugin-pwa` 预缓存外壳 + 已玩过的游戏资源，支持“添加到主屏幕”、离线可玩（阶段 1 接入）。
- 版本更新：Service Worker 采用 `prompt` 模式，避免小朋友玩到一半被刷新打断。

### 2.9 明确“暂不做”（Anti-scope）

账号系统 / 后端 API / 排行榜 / 多人联机 / 内购 / 广告 / 3D / 后台 CMS / 多语言（只做简繁 + 拼音）/ **vue-router（阶段 0 用 20 行 hash 路由，路由超过 5 条或需要嵌套路由时再引入 vue-router 5）**。

**理由**：这些都会显著抬高成本与合规风险，且对“让孩子记住典故”这个核心指标几乎无贡献。等内容资产超过 20 个典故、确实需要非程序员来编辑内容时，再引入 CMS。

## 3. 架构设计

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  外壳 apps/site  (Vue 3.5 SFC)                               │
│  大厅 · 历史长卷 · 典故图鉴 · 复习中心 · 设置 · 家长中心        │
│  ── 状态：Pinia ── 路由：hash composable ── 样式：Tailwind     │
└───────────────┬─────────────────────────────────────────────┘
                │  动态 import（代码分割，Phaser 只在这里出现）
                ▼
┌─────────────────────────────────────────────────────────────┐
│  游戏包 games/<id>   ← 一个典故 = 一个包（可独立开发/测试/发布） │
│   scenes 编排 (Phaser)         logic/ (纯 TS：规则，可单测)     │
└───────────────┬─────────────────────────────────────────────┘
                │  只依赖下面这些，绝不反向依赖外壳
                ▼
┌──────────────┬──────────────┬──────────────┬────────────────┐
│ game-kit     │ templates    │ content      │ phaser-kit     │
│ 契约/事件     │ 玩法模板库    │ 典故数据+校验 │ 引擎启动/主题   │
└──────────────┴──────────────┴──────┬───────┴────────────────┘
                                     │
                        ┌────────────┴───────────┐
                        │ progress   │ platform  │  存档/复习调度 · 存储/音频/生命周期
                        └────────────┴───────────┘
```

`game-kit` 与 `content` **不含 Phaser 依赖**，所以外壳可以安全地 import 它们。

### 3.2 仓库结构（pnpm workspace）

```
CHAGS/
├─ apps/
│  └─ site/                     # Vue 3.5 外壳
│     └─ src/{views,components,stores,shell,registry.ts,router.ts}
├─ packages/
│  ├─ game-kit/                 # GameModule 契约、GameContext、事件类型（无 Phaser）
│  ├─ content/                  # 典故 JSON + zod schema + 校验 CLI
│  ├─ templates/                # 玩法模板：story / balance / quiz …（依赖 Phaser）
│  ├─ phaser-kit/               # Phaser 启动器、主题、基础场景（依赖 Phaser）
│  ├─ platform/                 # PlatformServices Web 实现：存储/音频/生命周期
│  └─ progress/                 # 存档、图鉴、复习调度（纯 TS）
├─ games/
│  └─ caochong-elephant/        # 曹冲称象（阶段 0 样板）
├─ e2e/                         # Playwright
├─ docs/
└─ scripts/
```

> 为什么一上来就用 workspace 而不是单应用：合集的目标形态是“30+ 个游戏包”，边界越早划清越省事。如果最终只做 3 个游戏，多出来的成本也就是一个 `pnpm-workspace.yaml`。**注意：脚手架阶段不引入 Turborepo/Nx**，pnpm script 足够，避免过度工程。
> 包之间用 `"exports": { ".": "./src/index.ts" }` 直连源码（just-in-time package），**不设构建步骤、不配路径别名**，改一处全仓即时生效。

### 3.3 核心契约（整个架构的心脏）

`games/*` 只依赖这份契约，外壳也只依赖这份契约——两边可以并行开发、独立替换。

```ts
// packages/game-kit/src/contract.ts
export interface GameManifest {
  id: string;                        // 'caochong-elephant'，与典故内容 id 一致
  title: string;                     // '曹冲称象'
  version: string;                   // semver，用于存档迁移
  template: TemplateId;              // 主玩法模板 id，如 'substitution'
  orientation: 'portrait' | 'landscape';
  designSize: { width: number; height: number };   // 逻辑分辨率 750×1334
  ageRange: [number, number];        // [7, 10]
  sessionSeconds: [number, number];  // 单局时长 [120, 300]
  skills: string[];                  // ['观察', '等量代换']
  curriculum: { dynasty: string; yearApprox?: number; figures: string[] };
  assets: { cover: string };
}

export interface GameEventMap {
  'session:start':  { at: number };
  'beat:enter':     { beatId: string };
  'choice:made':    { beatId: string; choiceId: string; correct: boolean; latencyMs: number };
  'hint:used':      { beatId: string; level: number };
  'level:complete': { levelId: string; stars: 0 | 1 | 2 | 3; mistakes: number; durationMs: number };
  'card:unlocked':  { entryId: string; cardId: string };
  'session:exit':   { reason: 'complete' | 'quit' | 'background'; progress: number };
}

export interface GameContext {
  container: HTMLElement;
  manifest: GameManifest;
  content: ContentEntry;          // 该典故的全部内容数据
  services: PlatformServices;        // storage / audio / lifecycle / share / telemetry
  locale: 'zh-CN' | 'zh-TW';
  reducedMotion: boolean;
  debug?: { seed?: string; skipIntro?: boolean; autoplay?: boolean };
  emit<K extends keyof GameEventMap>(type: K, payload: GameEventMap[K]): void;
  requestExit(): void;               // 把控制权交还外壳
}

export interface GameModule {
  manifest: GameManifest;
  mount(ctx: GameContext): Promise<void>;   // 内部 new Phaser.Game(...)
  unmount(): Promise<void>;                 // 必须 game.destroy(true)，零全局残留
  pause(): void;
  resume(): void;
}
```

**Vue 宿主组件**（外壳里唯一需要认识 Phaser 的地方）：

```vue
<!-- apps/site/src/views/PlayView.vue -->
<script setup lang="ts">
import { onBeforeUnmount, onMounted, shallowRef, useTemplateRef } from 'vue';
import { registry } from '@/registry';
import { createGameContext } from '@/shell/createGameContext';
import type { GameModule } from '@chags/game-kit';

const host = useTemplateRef<HTMLDivElement>('host');

let disposed = false;

onMounted(async () => {
  const load = registry[props.gameId];
  if (!load) throw new Error('unknown game: ' + props.gameId);
  const m = (await load()).default;
  if (disposed) return;
  mod.value = m;
  await m.mount(createGameContext(m.manifest, host.value!));
});

onBeforeUnmount(async () => {
  disposed = true;
  await mod.value?.unmount();             // ★ 必须销毁 Phaser，否则残留 canvas 与 RAF 循环
});
</script>

<template>
  <div ref="host" class="game-host" />
</template>
```

### 3.4 玩法模板库 —— 让“第 30 个典故”变便宜

这是整个方案里最重要的一个设计。没有它，30 个典故就是 30 份从零开始的游戏代码。

**公式：一个游戏 = 若干模板（骨架）+ 一份内容 JSON（血肉）+ 专属美术与叙事（气质）+ 约 20% 定制代码。**

一个典故可以由**多段模板串起来**（内容里写成 `game.stages`），也可以插入**游戏专属场景**。
盘古就是三者的组合：

```
story（开场两幕）→ chaos（专属：连点蛋壳，混沌炸开）
                  → grow（撑天：连点 30 次，一万八千年）
                  → place（化身：6 团光回到日月山河）
                  → reward（典故卡）
```

| 模板 id | 交互原语 | 适配的典故类型 | 已用于 | 状态 |
|---|---|---|---|---|
| `story` | 分幕绘本 + 旁白（所有游戏共用开场） | 通用 | 全部 | ✅ 已实现 |
| `substitution` | 拖拽 + 水痕：等量代换 | 原理与转化 | 曹冲称象 | ✅ 已实现 |

| `place` | 把东西拖到它该去的地方 | 归属、转化、修补 | 盘古化身、女娲补天 | ✅ 已实现 |

每个模板通过**工厂函数**产出绑定了内容的场景类，游戏包只负责“串场景”：

```ts
// games/caochong-elephant/src/index.ts

createBalanceScene(ctx, levelScript)          // 等量代换玩法
createQuizScene(ctx, questions)               // 巩固测验
createRewardScene(ctx)                        // 典故卡 + 完成
```

**取舍说明**：模板化有“玩起来都一个味儿”的风险。对策是硬性要求——每个典故必须在内容里声明一个 `keyMoment`（关键抉择点），模板只提供交互原语，叙事、美术、反馈、音效全部专属。目标比例：**60% 复用 / 40% 定制**。

### 3.6 “记住典故”的记忆工程（五层机制 → 技术落点）

| 层 | 机制 | 技术落点 |
|---|---|---|
| L1 | **情境代入**：不是读故事，是“做”故事 —— 而且**必须听完** | `story` 模板分幕绘本 + 旁白；旁白念完才发 `story:ready` 放行；玩家扮演典故中的角色 |
| L2 | **关键抉择**：必须自己找到那个办法（aha moment） | `keyMoment` + `misconceptions`；选错给“引导式提示”而不是直接给答案（`hint:used` 事件） |
| L3 | **多通道编码**：看 + 听 + 做 + 说 + 选 | 画面 / 旁白 / 操作 / 跟读成语 / 填空选择 |
| L4 | **收集与结构**：典故卡 + 历史长卷 | 通关解锁 `card:unlocked`；卡片按 `yearApprox` 落在长卷上，形成“我点亮了中国历史”的成就感 |
| L5 | **间隔重复 + 迁移**：1/3/7/21 天后再见 | `ReviewScheduler`（纯 TS，简化版 SM-2）；复习关卡自动从 `quiz`（含 `kind: transfer`）生成 |

历史长卷是合集的**主线**（而不只是一个菜单）：横向时间轴，从先秦到明清，已学典故点亮成卡片，未学的显示为剪影。它把“玩游戏”变成“收集与探索”，也是把 30 个独立小游戏粘成一个“合集”的关键。

```ts
// packages/progress/src/review.ts —— 纯函数，可单测，无副作用
export function nextReview(state: ReviewState, grade: 0 | 1 | 2 | 3, now: number): ReviewState {
  const INTERVALS = [1, 3, 7, 21, 60]; // 天
  const level = grade >= 2 ? Math.min(state.level + 1, INTERVALS.length - 1)
                           : Math.max(state.level - 1, 0);
  return { ...state, level, dueAt: now + INTERVALS[level] * 86400000, lastGrade: grade };
}
```

### 3.7 儿童向的交互与安全规范（写进 code review 清单）

- 可点击区域 **≥ 88×88 逻辑像素**；按钮不做悬停依赖（触屏没有 hover）。
- **无失败惩罚、无倒计时压力、无限重试**；错了只是“再想想”。
- **故事必须听完**：旁白结束前不放行（没有语音的设备按“读一遍”的时间兜底）；难度只加在“要多做几步、要更准一点”上。
- 全部关键文本**配拼音 + 旁白**；字号下限 28px（逻辑像素）。
- **不靠颜色单独传达信息**（色盲友好）：对/错同时用图标与音效区分。
- 单局结束提示休息；连续游玩 20 分钟弹“眼睛要休息啦”。
- **家长锁**：退出游戏、进入设置、清除存档需长按 3 秒。
- 尊重 `prefers-reduced-motion`，提供“减少动画”开关。
- 无广告、无外链、无社交分享诱导、不采集儿童个人信息（遵循《未成年人网络保护条例》《儿童个人信息网络保护规定》）。

### 3.8 平台适配层（为微信小游戏留门）

`PlatformServices` 是唯一的平台出口：

```ts
export interface PlatformServices {
  storage: ProgressStore;         // Web: IndexedDB   | 小游戏: wx.setStorage
  audio: AudioBus;                // 含 iOS 解锁与静音策略
  lifecycle: LifecycleBus;        // 前后台切换、暂停
  share(opts: ShareOptions): Promise<void>;
  telemetry: Telemetry;           // 默认 no-op（本地缓冲，绝不上报个人信息）
  now(): number;
}
```

**但必须诚实说明**：微信小游戏不是“换个适配器就能上”。需要额外处理 WebGL 上下文差异、包体限制、`wx` 全局注入、资源加载器替换。**结论与决策规则：**

- 如果**微信小游戏是硬性首发要求** → 现在就应改用 Cocos Creator，或先花 2–3 天用 Phaser 3.90 + `weapp-adapter` 做一次 **PoC 验证**再定；
- 如果**首发是 H5（浏览器 / 微信内网页 / PWA）** → 本方案最优，小游戏作为阶段 3 的可选分支。

**当前按后者执行**（首发 H5、手机竖屏优先）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **美术产能是最大瓶颈** | 30 个典故 = 大量素材，容易做不完 | 统一风格指南 + 组件化素材库；先完整打磨 1 个典故作为“视觉样板”；阶段 0 先用几何占位不阻塞 |
| 玩法同质化 | 玩久了都像选择题 | 模板 ≥ 8 个；每典故必须有 `keyMoment`；强制 40% 定制 |
| 微信小游戏移植不确定性 | 若首发就要小游戏会返工 | 见 3.8 的决策规则；必要时先做 2–3 天 PoC |
| 字体/音乐/音效版权 | 商用后收到侵权通知 | 只用明确可商用的资源，建 `ASSETS-LICENSES.md` 台账 |
| 历史内容准确性 | 儿童教育产品，错了伤害信任 | 内容必须带 `source.book` + 原文引用；建立审核清单，逐条对出处 |
| 中文全字库体积 | 首屏被字体拖垮 | 子集化 + 按需加载 |
| iOS/微信音频不响 | 小朋友以为坏了 | 在外壳的首次点击里统一解锁音频，进游戏前做自检 |
| **Vue 响应式代理吃掉 Phaser 实例** | 卡顿 / 直接报错 | `shallowRef` / `markRaw`；禁止 KeepAlive 包裹游戏容器；HMR 整页刷新（见 2.2） |
| **TypeScript 7 无法用于本项目** | 工具链直接崩 | 已实测并锁定 TS 5.9.3；升级前必须先验证 vue-tsc 兼容性 |

## 7.1 曹冲称象重做：从「点按钮」到「动手做」（2026-10-13）

第一版做出来后被判定「太死板、文字太多、说教」。复盘出的问题是：**把「关键抉择」做成了文字选择题**，
把「记住典故」做成了读故事 + 答题 —— 孩子始终在**读**，没有在**做**。

### 改动对照

| 维度 | 改前 | 改后 |
|---|---|---|
| 故事 | 4 幕 + 下一幕按钮 | 2 幕，点哪都行，每屏一句话 |
| 关键抉择 | 三选一的文字题 | **不做题**：让玩家自己试出来 |
| 玩法 | 点石头按钮，看数字涨 | **拖拽**大象与石头，看水痕 |
| 结算 | 文字测验 3 题 | 石头过秤，数字累加出 3000 |
| 屏幕文字 | 每屏 1–2 句 + 题目 | 几乎没有，靠图形 / 动画 / 音效 |

### 四段式（可复用的「等量代换」叙事骨架）

1. **直接称** → 秤被压垮：体验「称不动」，问题是被玩家自己撞见的
2. **象上船** → 船沉、留下水痕：发现「船能记录重量」
3. **刻一刀** → 玩家亲手把水痕刻下来
4. **换石头** → 搬到水痕回到水面：**这就是等量代换本身**
5. **称石头** → 数字累加：闭环完成，大象 = 3000

keyMoment 数据仍然保留，但**不再渲染成选择题**：它提供揭晓语与复习题，
「关键抉择」改由交互本身承载。

### 技术沉淀（都已进 phaser-kit，后续典故直接复用）

- cartoon.ts：圆润卡通绘制原语（厚描边圆角矩形、落地阴影、波浪水面、星光、涟漪、小手、挤压回弹）
- drag.ts：createDragController —— **不依赖 GameObject 命中区域**，改为「抓住半径内最近的目标」

### 一个值得记下来的坑

Phaser 4 里 Container.setInteractive(hitArea) 的局部坐标约定与直觉不符：
实测**点在 A 上却抓到了 80 像素外的 B**（按钮那种「点在正中心」的场景察觉不到，拖拽一上来就暴露）。
改成自己按距离判定后，既确定又对小朋友更友好 —— 手指粗、点不准也能抓住。

### 阶段 1 · MVP（约 4–6 周）
**做**：大厅 + 历史长卷 + 典故图鉴 + 复习中心 + 设置/家长锁；**3 个模板 × 4 个典故**（共 12 个）；PWA 离线；真美术与配音。
**验收**：孩子在无人指导下能自己玩完 4 个典故并说出寓意；离线可玩；连续游玩 20 分钟无崩溃。

### 阶段 2 · 扩充（持续）
**做**：模板扩到 8 个，典故扩到 20–30 个；间隔重复真正跑起来；低端机降级策略。
**验收**：新增一个典故的工时较阶段 1 下降 ≥ 50%（模板与工具链的复利体现）。

### 阶段 3 · 平台化（可选）
**做**：云存档（换 `PlatformServices.storage` 实现）、账号、家长端报告、微信小游戏 PoC/移植。
**验收**：换实现不改游戏包代码。

## 7.2 第二部：盘古开天辟地（2026-10-13）

神话与信史的处理不同：曹冲称象是"解题的聪明"，盘古是"创造的壮阔 + 把自己交出去"。
内容模型为此新增了 `kind: 'history' | 'myth'`，神话用 `yearApprox: -9999` 落在历史长卷最左端，
形成"从神话到信史"的时间纵深。

### 新增两个模板（都为后续典故服务）

- **grow（坚持）**：连点发力让一件事持续长大。复用面：愚公移山、精卫填海、铁杵磨针、闻鸡起舞、卧薪尝胆
- **place（归位）**：把东西拖到它该去的地方。复用面：孔融让梨、完璧归赵、负荆请罪

"点蛋壳炸开"那一段做成**游戏专属场景**（`games/pangu/src/scenes/chaos.ts`），不进模板库 ——
这正是"60% 复用 / 40% 定制"里那 40% 的落点。

### 三个设计决定

1. **把"坚持"变成手指的酸**：天日高一丈、地日厚一丈、盘古日长一丈，直接变成"每点一次，天升一丈、
   那个人在画面里被拉长一截"，30 次点满一万八千年。音调随高度上升，进度是听得见的。
2. **零失败的归位**：拿起一团光，它该去的位置自己发光。孩子靠"形状 + 提示"完成配对，全程无文字；
   每归位一件，用**语音**念出原文（"左眼变成了太阳"）——用听，不用看。
3. **对"死"的处理**：全程没有死亡表现。盘古是「躺下 → 化成光 → 光一件件回到世界」，
   配柔和音效。画面的语言是"他变成了世界"，而不是"他死了"。

### 实测

- `pnpm verify` 全绿；端到端 **6 项通过**（含盘古真实操作全流程：点蛋 4 次 → 连点 30 次 → 拖 6 团光归位）
- 生产产物：外壳 **60.6 KB gzip**（不含 Phaser）；两个游戏各自只有 3 KB / 7 KB 的业务 chunk，
  Phaser 是共享 chunk，只在进入游戏时加载

## 7.3 中英文双语（2026-10-13）

需求：整个项目支持中英文切换 —— 界面、典故内容、语音、文档都要。

### 分层做法

| 层 | 做法 | 为什么这么做 |
|---|---|---|
| **界面文案** | 新增 `@chags/i18n`：一张扁平的 key→文案表，中英各一份 | 通用标签（"开始玩"）不属于任何典故，不该塞进内容 JSON |
| **典故内容** | 中文写在 `entries/*.json`（保持可读），译文写在 `i18n/en/*.json`，结构镜像、只写要翻的字段 | 避免把 JSON 写成双语大杂烩；一部典故没翻译也能跑（回落中文） |
| **语音** | `AudioBus.speak(text, locale)`，TTS 按 `zh-CN` / `en-US` 选嗓音 | 将来上真人配音时，同样按 locale 取不同音频文件 |
| **文档** | `README.md` / `README.en.md`，`docs/` 与 `docs/en/` | 中英各自成篇，不做机翻拼贴 |

### 关键设计

1. **游戏本身不知道语言的存在**。外壳把 `getEntry(id, locale)` 的结果（已经翻译好的内容）交给游戏，
   游戏只读 `ctx.content`。所以新增语言 = 加一份翻译 JSON，游戏代码一行不改。
2. **构建期强制翻译完整**。`pnpm content:check` 会逐条检查：
   缺译文、字段对不上、数组长度不一致、译文合并后超长 —— 全都在 CI 阶段拦下，而不是等用户切语言才发现。
   文案表本身也有编译期保证（英文表少一个键就类型报错）+ 单测（中英文案不能完全相同，防复制粘贴漏翻）。
3. **语言优先级**：`?lang=` > 上次选择（localStorage）> 默认中文。`?lang=en` 让分享链接与自动化测试都能直接指定语言。
4. **切语言即重挂游戏**：`PlayView` 的 key 带上 locale，切换时卸载重建 Phaser 实例，避免半中半英的场景。

### 血泪教训：版面不能按中文的长度硬编码

上线后发现英文版**典故卡糊成一团**：标题冲出卡片、星星压住寓意、"出处"压在原文上。
原因是卡片早期用固定纵坐标排版 —— 中文"曹冲称象"五个字，英文 "Cao Chong Weighs the Elephant" 三十个字母，
固定坐标必然重叠。

修复：`reward` 改成**先量后排**的流式版面 —— 每个文字块统一按卡片内宽换行，量出高度后依次堆叠，
卡片高度由内容决定；万一内容仍超出可用高度，整体等比缩小，**宁可小一点也不重叠**。
按钮位置固定不变，自动化用例的坐标因此不受影响。

> 教训：任何"文字放进固定容器"的地方，都必须先量后排。中英混排会把这类问题一次性照出来。

### 双语版面巡检（新增 `pnpm audit:i18n`）

把两部游戏在**两种语言下共 34 个画面**全部截图到 `.scratch/i18n-audit/`（不入库）。
改文案、加语言、动版面之后跑一次，人眼扫一遍即可 —— 这次的卡片问题就是它照出来的。

### 实测

- `pnpm verify` 全绿；端到端 **8 项通过**，其中一项专测中英切换：界面、典故标题、典故卡、
  以及"切完语言刷新还记得住"
- 双语版面巡检 4 项通过（34 张截图）
- 首屏 shell 63.4 KB gzip（多出的是文案表与语言状态，预算 150 KB 内）

对全仓库做了一次审查（代码、测试、无障碍、CI 四个方向），以下是结论与处置。

### 修掉的问题

| 类别 | 问题 | 处置 |
|---|---|---|
| **CI 盲区** | 28 条端到端**从不在门禁里跑**；workflow 只在打 tag 时触发 | 新增 `ci.yml`：push/PR 跑类型/lint/单测/内容校验/构建，另起 job 跑 e2e 与生产产物用例；双语巡检在主干上跑并把截图传成 artifact |

| **玩家看到报错原文** | 关卡数据校验失败时，屏幕上直接是 zod 的 `[{ "origin": "string", "code": "too_big" ... }]` | 改成一句人话 + "回游戏馆"按钮；技术详情进控制台与 `window.__chags.lastError` |
| **315 行样板** | 7 个游戏包的 index.ts 里，15 行生命周期代码**一字不差**，典故卡配置也几乎一样 | 抽出 `defineGame()`：一个典故只剩"怎么画分幕、玩法场景怎么拼"。7 个文件 584 → 313 行 |

| **里程碑不可观测** | `fireMilestones` 不发事件 —— 把 pause 删掉、把三条里程碑合成一条，所有测试都会绿 | 发 `beat:enter:milestone:<id>`；e2e 断言夸父到河边时**尚未通关**、愚公三个里程碑**按序各出现一次** |

## 7.5 第二辑：神农 / 大禹 / 太公 / 烽火 / 杞人（2026-10-14）

方案见 [第二辑五典故方案.md](第二辑五典故方案.md)。这一批要解决的是**同质化**：
已有七部的动词是 称 / 补 / 射 / 填 / 追 / 挖 / 撑，再来五个"连点涨进度"就是第六次换皮。
于是每部给一个只属于它的动词：**尝 / 疏 / 等 / 点 / 解**，以及一张签名画面。

### 新增三个模板 + 一个专属场景

| 模板 | 玩法核心 | 复用于 |
|---|---|---|
| `sort` | 分类归位；带可选 `probe`（**先尝后分**：没尝过就放不进木牍，会被送回嘴边） | 神农尝百草；田忌赛马、对症下药等"辨别"类 |
| `trace` | 手指划路，按顺序过锚点。**只看顺序，不看手感**：划歪不倒退、划断能接着划 | 大禹治水；都江堰、郑国渠、张骞通西域 |
| `wait` | 等。诱惑会让终点后移但**有上限**，最后要做一个收束动作（收起直钩） | 太公钓鱼；苏武牧羊、卧薪尝胆、程门立雪 |

烽火戏诸侯是一次性机制（点一次火 → 信任少一格 → 真的来了没人来），做成**游戏专属场景**
（`games/fenghuo/src/scenes/beacon.ts`），但关卡数据用 `beacon` schema 登记在模板层 ——
这样双语校验、schema 体检照样覆盖它（与盘古专属的开蛋场景同一套做法）。

### 三个设计决定

1. **"先尝后分"是数据约束，不是文案**：`SortLevelSchema` 强制"有 probe 就必须给每件东西写
   `tastedKind`"，内容写漏了构建期就报错 —— 教学核心不能靠自觉。
2. **"等"按墙钟算，而且永远等得到**：`wait` 沿用夸父那次的教训（不累加帧 delta，慢手机与 CI 一致）；
   `penaltyCap` 保证诱惑最多把终点推后几次，推满之后只回应、不再延后。
3. **信用是点出来的，不是讲出来的**：烽火的信任格数就是数据里的 `decoyRounds`，
   孩子每点一次火少一格；全篇没有一句说教文案，教训落在点火的人身上。

### 顺手修掉一个公共层问题

故事页"点哪都行"的小手固定在 `H-150`，而正文从 985 开始排版：中文 3 行、**英文 4 行**时
最后一行会被小手压住（12 部典故的双语巡检都会看到）。现在小手按正文实测高度定位，
实在放不下就挪到右下角；`STORY_TEXT_Y` 也从 985 提到 950。

## 7.6 第三辑：刻舟求剑 / 朝三暮四 / 狡兔三窟 / 百步穿杨 / 庖丁解牛（2026-10-14）

方案见 [第三辑五典故方案.md](第三辑五典故方案.md)。这一辑要解决的是**同一时代、同一题材**：
五则全落在春秋战国，又都是"讲道理"的故事 —— 再来五个"拖到对的地方"就是第七次换皮。
于是每一则仍然只给一个属于它的动词：**刻 / 分 / 凿 / 练 / 游**，并各配一张签名画面。

### 新增三个模板 + 一次扩展 + 一个专属场景

| 模板 | 玩法核心 | 复用于 |
|---|---|---|
| `mark` | 在**会动的世界**上做记号：会漂的面跟着船走，不动的面一动不动。判定就一句"记号此刻在世界里的位置差多少" | 刻舟求剑；荆人涉澭、郑人买履、守株待兔 |
| `split` | 总量不变的两份分配 + 观众反应。东西串在一条绳上，动的只有中间那块木牌 | 朝三暮四；不患寡而患不均、二桃杀三士 |
| `burrow` | 预留退路：危险一次守住 `blocks` 个洞口，**洞口比它多一个才躲得过** | 狡兔三窟；曲突徙薪、未雨绸缪 |
| `aim`（扩展） | 可选的距离阶梯（`ladder`）+ 每靶半径（`target.radius`）。后羿的数据一个字段都没改 | 百步穿杨；纪昌学射、惊弓之鸟 |
| `butcher`（专属场景） | 顺缝推块 + 刀口状态。数据仍登记在模板层，双语与 schema 体检照常覆盖（同 beacon / chaos 的做法） | 庖丁解牛 |

### 四个设计决定

1. **"三窟"是数据逼出来的，不是文案讲的**：`BurrowLevelSchema` 里最凶的一次危险 `blocks: 2`，
   洞口必须比它多一个才有路走 —— 孩子是被狐狸逼着去挖第三个洞的。schema 还挡两种写歪的内容：
   "无论怎么挖都躲不过去"（blocks ≥ 洞口总数）和"缝的方向太雷同"（butcher 的骨架像同一个动作）。
2. **记号刻在哪儿，差别看得见**：刻舟求剑不解释"参照系"三个字 —— 剑一直在画面里、
   船一直在走，刻在船帮上的刻痕随船漂移。捞空一次之后，正确的那块地方才发光（零失败）。
3. **一开始就撞一次，是玩法的一部分**：庖丁的第一刀一定砍在骨头上（"当"一声、刀口多一个缺口），
   然后缝才亮起来；最后两块**不给提示**，凭记住的结构自己推 —— 这就是原文的三段。
4. **危险还在演的时候也能接着挖**：狡兔三窟的第一次实现把"危险中"的点击吞掉了，
   孩子点了没反应；现在危险照样演，他可以在狐狸守着洞口的时候去挖下一个 —— 挖通了这一趟立刻再来。

### 顺手补上的两种定性

`kind` 之前只有"神话 / 传说 / 信史"，而这一辑有三则是寓言（刻舟求剑、朝三暮四、庖丁解牛），
标成"信史"不诚实。内容模型加了第四个值 `fable`（寓言），游戏馆多一枚徽章，
第二辑的杞人忧天也一并改标。

### 实测

| 验收项 | 结果 |
|---|---|
| `pnpm verify`（类型 → lint → 单测 → 内容校验 → 构建 → 体积） | ✅ 全绿 |
| 单元测试 | ✅ **227 项通过**（31 个文件；三个新模板 + 五部游戏各有判定单测） |
| 单测增量 | 156 → **227**（`mark` 13 / `split` 13 / `burrow` 12 / 五部游戏 34 / `aim` 阶梯等） |

| 内容 | 17 个典故 × 2 语言：`content:check` 全过（含英文关卡脚本重新过 schema） |

### 踩到的两个坑（都值得记下来）

1. **"提示"必须按未来的状态算，不能按此刻算**：刻舟求剑重来之后，若按"此刻船还在上游"去挑
   哪个面管用，提示会又指回船帮 —— 正确做法是按"这一次会漂多远"算。端到端里那条
   autoplay 用例直接卡在这一条上（无限捞空）。
2. **测试里的固定等待会骗人**：狡兔三窟的用例在"危险演出中"去挖洞，点击被吞掉，
   看起来像游戏坏了。修法是两边都改：场景允许危险期间继续挖，用例改成等事件而不是等秒数。

## 7.7 听完故事才能继续 + 难度整体上调（2026-10-15）

### 为什么改这两件事

用户的原话是：*“适当提高每个小游戏的难度，并强制听完故事才能继续，这两点主要是保证游戏玩家能完整的了解典故。”*
两件事指向同一个目标 —— **让"听过"变成"必须用上"**：
故事页现在是不可跳过的正片，动手环节则不再能靠两三下蒙过去。

### 一条新的契约：`speak` 要能回报"念完了"

`AudioBus.speak()` 以前返回 `void`，故事页无从知道旁白念完没有。现在返回 `SpeechHandle`：

```ts
export type SpeechOutcome = 'ended' | 'unavailable';
export interface SpeechHandle { readonly done: Promise<SpeechOutcome>; }
```

三条实现路径都要 resolve，一条都不能少（否则故事页会永远停在"正在听"）：

| 环境 | 路径 | 结果 |
|---|---|---|
| 安卓壳 | 原生 TTS `speak()` 的 Promise | 念完 → `ended`；没装语音包 → `unavailable` |
| 浏览器 / WebView2 | `SpeechSynthesisUtterance` 的 `onend` / `onerror` | 念完 → `ended`；报错 → `unavailable` |
| 静音 / 没有 TTS API | 直接返回 | `unavailable` |

### 放行算法（纯函数，`packages/templates/src/story.logic.ts`）

- 有语音且**念得够久**：`ended` → 立刻放行。
- "念得太快"（无头浏览器、没装语音包、刚被 cancel）：不算听过 —— 补足"读一遍"的时间。
  中文按 5 字/秒、英文按 14 字符/秒，夹在 2.2 ~ 24 秒之间。
- 看门狗：`读一遍 × 1.8 + 2.5 秒` 还没有回报，一律按 `unavailable` 处理，绝不把孩子钉在这一幕。

放行时发 `story:ready`（调试桥记成 `story:ready:s1`），e2e 用它确定性地翻页。
提前点只给一句 `story.listenFirst`（"先听完这个故事"），不翻页。

### 调试开关

- `?autoplay=1`：自动通关（原有），跳过等待。
- `?story=instant`：截图巡检与"只关心玩法"的 e2e 用，跳过等待但保留故事页画面。
- 顺手删掉了从未被使用过的 `DebugOptions.skipIntro`。

### 难度：口径是"多几步、判定收紧"，不是"更容易失败"

改了 17 部典故的关卡数据与 8 个宽容度常量（`PLACE/SORT/SPLIT/MARK/BURROW/WAIT/TRACE` 的
`dropForgive / carveForgive / digForgive / dividerRadius / temptationRadius`），
以及各场景"卡住才提示"的空转时间。具体见 README 的《两条硬规矩》。

两条必须一起改的"镜像"（本次专门踩到）：

1. `games/yangyouji/src/layout.ts` 的 `LEAF_RADII` 既用于**画柳叶**也用于**判定** ——
   只改 JSON 会让"画得比判定大"。测试 `logic.test.ts` 守着这条一致性。
2. `games/qiren/src/art.ts` 的 `BUBBLE` 必须等于关卡数据里的 `slot.radius`；`games/paoding/src/layout.ts`
   的 `PIECES` 必须等于 butcher 脚本里的骨块。

### 实测

- 单元测试 238 项全绿（新增 `story.logic.test.ts` 11 项）；`content:check` 全绿（17 典故 × 双语）。
- e2e 新增《故事必须听完：旁白没念完之前，怎么点都不翻页》；其余 20 条玩法用例改用
  `?story=instant`，把等待留给这一条专门守。

## 7.8 分组：小游戏合集从“一堆典故”变成“有结构的合集”（2026-10-15）

### 为什么现在做

下一批游戏是**三十六计**，它不属于“典故”。如果等到内容进来了再补结构，
大厅、图鉴、注册表、内容体检会各自长出不同的假设；而且分组**以后肯定不止两组**，
写死“典故 / 三十六计”的二分法必然要重写。所以先把分组做成一等公民，再加游戏。

### 分组表就是唯一的事实来源

```ts
// packages/content/src/groups.ts
export const GROUPS = [
  { id: 'allusion',  order: 10, orderBy: 'year'  },  // 典故：按年代
  { id: 'stratagem', order: 20, orderBy: 'index' },  // 三十六计：按计策序号（登记顺序）
] as const satisfies readonly GameGroup[];
```

由此派生的三个决定：

1. **空组也要出现**。三十六计现在还没有游戏，但大厅必须给它一个位置
   （显示“敬请期待”），否则“分组”只是数据结构里的一行，用户看不见。
   `groupBy()` 因此按 `GROUPS` 遍历，而不是按“有内容的组”遍历。
2. **组内排序是分组自己的属性**。典故按 `yearApprox`（历史长卷从上古走到明清），
   三十六计按 `orderBy: 'index'` —— 计策的先后与年代无关，按年代排会把序号打乱。
3. **`group` 必填、无默认值**。忘了写就构建期报错，不会悄悄归到“典故”里。
   `content:check` 另外会打印每一组的条目数，并拦住没登记的分组 id。

### 三层各自负责什么

| 层 | 负责 | 位置 |
|---|---|---|
| 内容层 | 分组表（id / 顺序 / 组内排序）、每条内容的 `group` | `packages/content/src/groups.ts`、`entries/*.json` |
| 文案层 | 分组名 / 一句话 / 空状态：`group.<id>.title` / `.note` / `.empty` | `packages/i18n/src/messages.ts` |
| 界面层 | 按分组渲染分区；**不认识任何具体的组** | `HallView.vue` / `AlbumView.vue` |

文案层用类型把“少写一条”变成编译错误：
`Record<\`group.${GroupId}.${'title'|'note'|'empty'}\`, string>` —— 新增分组时忘了补文案，`pnpm typecheck` 直接红。

### 大小写一处没变的地方

内容集合仍然叫 `allusions`（`ContentEntry`、`getEntry()`）：改名会波及 17 个游戏包与全部 e2e，
收益只是措辞。等三十六计真有游戏了，再连同 `kind` 一起做一次完整的“内容条目”改名，
那时才有第二份真实数据来验证新名字是否合适。

### 顺带统一了几个称呼

分组进来了，界面上的“典故馆 / 我的典故图鉴 / 个典故”就不再准确：
改成“游戏馆”（`hall.title` / `nav.hall`）、`hall.unit` 改“个游戏”、
`album.title` 改“我的图鉴”、`play.backToHall` 改“回游戏馆”。

### 实测

- 单测新增 `groups.test.ts`（9 项：分组表约束、空组保留、归档不漏不重、schema 拒绝未登记分组）
  与 `messages.test.ts` 的分组文案覆盖（每个组 × 3 个字段 × 2 种语言）。
- e2e 新增《分组：典故与三十六计各占一块，空组显示“敬请期待”》：
  两组都在、典故组 17 个入口（数量取自内容目录）、三十六计组 0 个入口且有占位说明，中英各验一次。

## 7.9 三十六计 · 批 0：内容条目改名（allusions → entries）与 stratagem 字段（2026-10-15）

### 为什么现在做

§7.8 结尾留了一句："等三十六计真有游戏了，再连同 `kind` 做一次完整的'内容条目'改名。"
现在三十六计的方案已经确认（见 [三十六计方案.md](三十六计方案.md)），第一批 6 计就要进来 ——
再不改名，36 条新内容会长在一个叫 `allusions`（典故）的目录里。

### 改了什么

| 位置 | 之前 | 现在 |
|---|---|---|
| 目录 | `packages/content/src/allusions/` | `packages/content/src/entries/` |
| 类型 | `AllusionContent` / `AllusionSchema` | `ContentEntry` / `ContentEntrySchema` |
| 集合 | `allusions` | `entries` |
| 取用 | `getAllusion` / `allusionsFor` / `allusionsByYear` / `localizedAllusion` | `getEntry` / `entriesFor` / `entriesByYear` / `localizedEntry` |
| 进度类型 | `AllusionProgress`（字段 `allusionId`） | `EntryProgress`（字段 `entryId`） |
| `kind` | history / myth / legend / fable | **+ `strategy`（兵法）** |
| 内容字段 | — | **+ `stratagem { number, set }`**（仅 stratagem 组） |

**没改的两处（刻意）**：

1. **分组 id 仍然叫 `allusion`** —— 那一组装的就是典故，改名没有收益；
2. **存档字段名仍然是 `SaveData.allusions`** —— 改名会让所有老存档读不出来（玩家的星星不能凭空消失）。
   `migrate()` 里补了一条：老存档里每个进度对象带的是旧字段 `allusionId`，读档时按外层的键回填 `entryId`。

### stratagem 的两个新约束

- `group === 'stratagem'` ⟺ 有 `stratagem` 字段（schema refine，两边的错法都在构建期报错）；
- `stratagem.set === ceil(number / 6)`：第 n 套 = 序号 6(n−1)+1 … 6n。

`content:check` 另外检查"**登记顺序 = 计策序号**"：三十六计这一组的组内排序是
`orderBy: 'index'`（登记顺序），顺序写错了大厅里第 5 计会排到前面去。

**按语写在 `source` 里**（book = 《三十六计·X套》，quote = 按语节选），`stratagem` 里只留结构性的
`number` / `set` —— 同一句原文不在一条内容里出现两遍。逐字确证不了的战例原文不编，
战例写进故事分幕与 `figures` / `era`（见第一辑方案第三节的引文状态表）。

### 顺带

- 界面：`hall.strategy`（兵法）徽章 + 卡片上的"第 n 计 · 胜战计"；中英句式不同，所以模板放文案表
  （`stratagem.card` = `'第 {n} 计'` / `'Stratagem {n}'`），数字由 `stratagemLabel()` 填；
- 文案层：`stratagem.set.1..6` 六套套名（中英各一份），与内容层的 `STRATAGEM_SETS` 对齐，`messages.test.ts` 守着；
- 图鉴卡也带"第 n 计 · 套名"。

### 实测

- `pnpm typecheck` / `pnpm lint` 全绿；单测 **257 项**（新增 19 项：分组与三十六计约束、套名文案、文案模板）；
- `pnpm content:check` 通过，分组体检打印 `allusion（17 个）/ stratagem（0 个，空组 → 敬请期待）`；
- e2e 在批 1 落地后统一重跑：批 0 期间与实现分支并行写过文件，dev server 的 HMR 会让截图用例假失败
  （首轮 `capture dayu screenshots` 就是这么挂的：页面在测试中途被整页重载，canvas 消失）。

## 7.10 三十六计 · 第一辑（胜战计 1–6）落地（2026-10-15）

方案见 [三十六计方案.md](三十六计方案.md)（总）与 [三十六计-第一辑方案.md](三十六计-第一辑方案.md)（本辑规格书）。

### 这一辑新增的五个模板

| 模板 | 机制一句话 | 覆盖 |
|---|---|---|
| `ruse` | 我做我的，你看到的是我想让你看到的（hide 换外壳 / divert 看时机） | 1 瞒天过海、6 声东击西 |

三条与既有模板一致、这一辑又强调了一次的规矩：

   单测与画面用的是同一份判定（`ruse` 的"被灯照到"、`window` 的"窗口关掉清零"都靠它守住）；
2. **每个模板必须实现 `runAutoplay()`**，且走的是与真实操作同一条路径（不是另写一条"自动通关"分支）；
3. **零惩罚**：被识破、白鼓、窗口关掉都只是退回与重来，不动星星、不结束。

### 实测

- 单测 **387 项**（新增 130；5 个模板的判定单测 88 项）；`content:check` 打印
  `allusion（17）/ stratagem（6）`；`pnpm verify` 六项全绿；
- 体积：首屏 104.7 KB / 150，最大懒加载 chunk 377.3 KB / 450，assets 1920 KB / 3500；
- e2e 72 条（新增 6 条 autoplay + 6 张玩法截图），分组用例改成"数量取自内容目录"
  —— 三十六计从 6 长到 36，这条用例一行都不用改；
- 双语版面巡检（`pnpm audit:i18n`）扩容到三十六计：新增调试开关 **`?card=hold`**
  （自动通关照跑，但停在典故卡上 —— 自动通关下卡片只停 200ms，不这样拍不到卡面），
  6 个游戏 × 中英 × 故事/玩法/卡面 全部截图人工过目；卡面是英文长标题最容易溢出的地方，
  实测无溢出。后面 30 计直接复用这套巡检。

### 一条测试上的教训

"不看时机就会被灯照到"这条用例，第一版用 progress 累加来模拟走路，东西其实没动过 ——
判定是对的，是**测试的模型**不对（永远撞不上灯）。改成把"走到哪儿了"真算成坐标再喂给
`isExposed` 之后，这条性质才真的被守住。教训：模拟玩家的用例，也要让被模拟的对象真的动起来。

## 7.13 内容摘要 / 详情拆分：首屏 125.5 → 78.3 KB（2026-10-15，第四辑之前）

### 为什么要做

第三辑落地后，体积门禁报出首屏 **125.5 KB**（预算 150）。查了一遍：涨的不是代码，是**内容**。
把首屏 chunk 里的字符串抓出来看，35 条内容的故事旁白、复习题、关卡字段全在里面 ——
大厅只是为了渲染卡片（标题 / 年代 / 寓意 / 关键词 / 出处），却把整套关卡脚本一起下了下来。
实测：内容合计 **265.7 KB 原始 / 65.4 KB gzip**，占首屏的 **52%**。
按每批约 +7 KB 的趋势，第 5–6 辑会顶穿预算。

### 怎么拆

每条内容拆成两半（字段划分只写在 `schema.ts` 的 `splitEntry()` 里）：

| 层 | 文件 | 内容 | 谁用 |
|---|---|---|---|
| 摘要 `EntrySummary` | `entries/<id>.json` | id / 分组 / 定性 / 标题 / 拼音 / 朝代 / 年代 / 出处 / 寓意 / 关键词 / 年龄段 / 计策字段 | 大厅、图鉴、注册表（**首屏**） |
| 详情 `EntryDetail` | `entries/<id>.game.json` | 人物 / 故事分幕 / 关键抉择 / 误解 / 复习题 / 关卡脚本 | 游戏包、内容体检 |
| 完整 `ContentEntry` | 由上面两半合并 | 全字段（构建期再校验一次） | 内容体检、游戏逻辑 |

配套的三件事：

1. **两个入口**：`@chags/content`（只有摘要）与 `@chags/content/full`（完整 + 摘要侧的一切）；
   游戏包与内容体检用后者，外壳用前者；
2. **`loadEntry()`**：外壳加载完整内容只走这一条动态 import —— Vite 因此把详情切成
   `detail-*.js`（154 KB 原始），**进入游戏时才下载**；
3. **机器守卫**：`eslint.config.js` 里对 `apps/site/**` 禁掉 `@chags/content/full`
   —— 一句 import 就能把懒加载作废，而体积门禁要到打包后才发现，所以在写的当下就拦住。

译文补丁同样分两半（`i18n/en/<id>.json` 与 `i18n/en/<id>.game.json`），
内容体检对两半分别做"结构镜像 + 合并后重过 schema + 零中文"。

### 实测

| 指标 | 拆分前 | 拆分后 |
|---|---|---|
| 首屏 JS + CSS（gzip） | 125.5 KB | **78.3 KB** |
| 首屏里有没有故事旁白 / 关卡字段 | 有 | **没有**（已用字符串探针验证） |
| 完整内容去哪了 | 首屏 | `detail-*.js`（154 KB 原始，进游戏时才下） |
| 单测 | 702 | 702（全绿；改了 17 个游戏测试的"读内容"方式） |

**一处实现上的教训**：用脚本重写这两个生成文件时，我用 `lastIndexOf('import ')` 找 import 段末尾，
结果被文件正文里的 `import` 字样骗到，把中间的非 JSON import 段整段切掉了 ——
typecheck 立刻把它抓了出来。教训：**生成文件时不要用"找最后一个关键字"这种脆弱切法**，
该显式拼整个文件就显式拼。

1. ✅ **技术栈**：Phaser 4.2 + **Vue 3.5** + Vite 8 + TypeScript 5.9.3 + pnpm workspace，H5 优先、无后端、本地存档。
2. ✅ **首发平台**：手机浏览器 / 微信内网页，竖屏优先，零安装门槛。
3. ✅ **美术与音频**：阶段 0 用几何图形 + WebAudio 合成音效 + 浏览器 TTS 旁白（零资源文件），把玩法与学习闭环先跑通。

5. ✅ **阶段 0 样板典故**：曹冲称象（浮力/等量代换最适合验证模板化是否成立）。
6. ✅ **美术风格**：圆润卡通（厚描边、落地阴影、几何绘制），不使用真人配音，旁白继续用浏览器 TTS。
7. ✅ **神话的数据模型**：新增 `kind`，神话排在历史长卷最左端（上古·神话）。
8. ✅ **第二个典故**：盘古开天辟地，同时落地 `grow` 与 `place` 两个可复用模板。
9. ✅ **双语**：界面 / 典故内容 / 语音 / 文档全部支持中英切换，翻译完整性由构建期强制。
10. ✅ **第三辑选型**：刻舟求剑 / 朝三暮四 / 狡兔三窟 / 百步穿杨 / 庖丁解牛 ——
    每则一个专属动词（刻 / 分 / 凿 / 练 / 游），复用与新增模板的取舍见 §7.6。
